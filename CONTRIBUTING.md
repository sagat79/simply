# Contributing

:smile: Thank you for contributing to Simply!

## Development

Simply uses [Gulp](https://gulpjs.com/) as a build tool and npm to manage front-end packages.

```bash
# clone this repo
$ git clone https://github.com/sagat79/simply.git

# go to the folder
$ cd simply

# link to ghost themes dir
$ ln -s $PWD path/to/ghost/content/themes/simply

# install the dependencies
$ npm install

# run build & livereload task
$ npm run dev

# restart ghost server
$ cd path/to/ghost && ghost restart --development
```

### Icons

[Ionicons](https://github.com/ionic-team/ionicons), generated by [Icomoon](https://icomoon.io/app/#/select) after importing `src/svg-icons/selection.json`.

### Build commands

- `npm run dev` — Compile assets when file changes are made, start livereload
- `npm run build` — Compile and optimize the files in your assets directory
- `npm run prod` — Compile assets for production and generate `dist/simply-v<version>.zip`

### Additional commands

- `npm run lint:js` — [Standard](https://standardjs.com/), check for errors in the scripts
- `npm run lint:css` — [Stylelint](https://stylelint.io/), check for errors in the styles
- `npm run lint` — Check errors in both scripts and styles
- `npm run scan` — [gscan](https://github.com/TryGhost/gscan), check for errors, deprecations, and other Ghost compatibility issues
- `npm run test` — Run `lint` and `scan` together

Before opening a PR or pushing anywhere, run the full local gate yourself:

```bash
npm ci && npm run prod && npm run lint && npm run scan && npx reuse lint
```

All four (build, lint, gscan, REUSE) must pass — this is exactly what CI re-checks on your PR (see below), so catching it locally first saves a round trip.

## CI checks on every PR

Every pull request against `dev` or `master` runs [`.github/workflows/ci.yml`](.github/workflows/ci.yml), which:

1. Installs dependencies and runs a full production build (`npm run prod`).
2. Verifies the built images in `assets/images/` weren't corrupted in the process (a real regression this theme's build pipeline has hit before).
3. Runs `npm run lint` (Standard + Stylelint) and `npm run scan` (gscan).
4. Checks REUSE/SPDX license compliance — **every file needs a copyright and license header**. If you add a new file, either write the header yourself or run:
   ```bash
   npx reuse annotate -c "Your Name <your@email>" -l GPL-3.0-or-later <file>
   ```

Two additional security checks also run on every PR (see [`.github/workflows/security.yml`](.github/workflows/security.yml)):

- **Dependency review** — flags any newly introduced dependency with a known vulnerability directly in the PR diff. This one blocks merge.
- **CodeQL** — static analysis for common JS vulnerability patterns. Currently informational (not required to merge) while a baseline of clean runs builds up.

PRs opened by the maintainer or by Renovate auto-merge once all required checks pass (see [`.github/workflows/auto-merge.yml`](.github/workflows/auto-merge.yml)); everyone else's PRs get full CI feedback and are merged by hand after a look.

## Git/GitHub workflow

This is our preferred process for opening a PR on GitHub:

1. [Fork](http://help.github.com/fork-a-repo/) the repo, clone your fork, and configure the remotes:

    ```bash
    # Clone your fork
    git clone https://github.com/<your-username>/simply.git

    # Navigate to the newly cloned directory
    cd simply

    # Assign the original repo to a remote called "upstream"
    git remote add upstream https://github.com/sagat79/simply.git
    ```

2. If you cloned a while ago, get the latest changes from upstream. `dev` is the active integration branch — base your work on it, not `master`:

    ```bash
    git checkout dev
    git pull upstream dev
    ```

3. Create a new topic branch (off `dev`) to contain your feature, change, or fix:

    ```bash
    git checkout -b <topic-branch-name>
    ```

4. When your changes are ready for review, push your branch and open a PR against `dev`:

    ```bash
    git push origin <topic-branch-name>
    ```

5. [Open a Pull Request](https://help.github.com/articles/using-pull-requests/) with a clear title and description, targeting `dev`.

6. When the changes have passed CI and been reviewed, they'll be merged for you.
